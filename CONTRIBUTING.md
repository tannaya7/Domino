# Contributing to the vendor knowledge base

The vendor knowledge base (`vendors/*.json`) is what lets this tool make claims like "Stripe runs
on AWS" or "an outage there is 99.99% available." Every claim in it needs to be either backed by a
real source or honestly marked as not backed by one. This file explains how to add or edit a
vendor entry.

**Reviewed PRs only.** There is no way to write to `vendors/*.json` anonymously or automatically —
every change goes through a pull request, which a human reviews, and CI (`npm run kb:check`) has to
pass before it can merge. See `.github/workflows/kb-check.yml`.

## Adding or editing a vendor

1. Read `vendors/schema.json` — every field is documented there.
2. Create or edit `vendors/<id>.json`. `id` must be kebab-case and match the filename.
3. Run `npm run kb:check` locally. It validates the schema and every cross-vendor invariant
   (unique ids, no package/env-prefix claimed by two vendors, https-only URLs, alternatives that
   actually exist) before you open a PR.
4. Run `npm run kb:generate` to regenerate `src/data/vendors.generated.ts`, and commit it alongside
   your `vendors/*.json` change — CI checks that generated file is up to date, not just that the
   source JSON is valid.
5. Open a PR. The issue template (`.github/ISSUE_TEMPLATE/vendor.yml`) is also a good starting
   point if you'd rather report something wrong without writing the JSON yourself — a maintainer
   can turn that into a PR.

## The substrate honesty rule

This is the one rule that matters most: **do not invent evidence.**

- `confidence: "verified"` — you have a real URL (the vendor's own architecture/security/trust
  page, or a first-party technical source) that says where this vendor runs. Put it in
  `substrate[].evidence`, along with the date you looked at it (`retrievedAt`) and a short note on
  what it actually says.
- `confidence: "reported"` — someone said this (a blog post, a prior version of this file, a DNS/IP
  finding that's suggestive but not conclusive — e.g. matched only at a CDN/edge layer), but it
  isn't independently confirmed. Still needs at least one evidence entry, but the note should be
  honest about the gap.
- `confidence: "unknown"` — you don't have a real source. This is not a bug or something to hide;
  leave `evidence: []` and, if you can, add a line to `docs/kb-todo.md` describing what you tried.
  **A schema validation error will catch you if you set `unknown` and still attach evidence, or set
  `verified`/`reported` with no evidence at all** — the rule is enforced, not just requested.

Never present a guess as a confirmation. "reported" and "unknown" are normal, useful states — most
of this project's own vendor entries are one of those two today (see `docs/kb-todo.md`).

## Where the data comes from, and where it doesn't

- `vendors/*.json` is hand-curated and reviewed. It is the only source of truth.
- `src/data/vendors.generated.ts` is generated by `scripts/generate-vendor-map.ts` from
  `vendors/*.json`. Never edit it by hand — regenerate it and commit the result.
- `scripts/verify-substrates.ts` (`npm run verify:substrates`) is an independent DNS/published-IP-
  range check — it never writes to `vendors/*.json` itself. Use its output
  (`public/substrate-verification.json`, `docs/substrate-verification.md`) as one input when you
  update a vendor's evidence, but always make the actual edit to `vendors/<id>.json` yourself, and
  read the finding before you cite it — an "agrees" verdict there means a direct (non-edge) match,
  which is worth `verified`; an edge-only or inconclusive result is not enough for `verified`.

## Fields at a glance

| Field | What it is |
|---|---|
| `id` | Stable kebab-case id, matches the filename. Never renamed once published. |
| `aliases` | Other detection strings (mainly other npm package names) for the same vendor. |
| `packages` | The primary package name per ecosystem (npm/pypi/go/gem/maven). `null` where not yet mapped for that ecosystem — never guess a package name you haven't checked. |
| `envPrefixes` | Env var names that identify this vendor. |
| `hosts` | Known global API hostnames, for `scripts/verify-substrates.ts`. Leave empty for vendors whose real endpoint is a per-tenant subdomain — don't guess a placeholder. |
| `statusFeed` | The vendor's public status-page API, if it has one in the Statuspage.io shape. |
| `substrate` | See "the substrate honesty rule" above. |
| `sla` | A published SLA number if you have one, `null` otherwise. `sourceUrl`/`retrievedAt` can be `null` even when `value` is set — most of today's SLA numbers are unsourced curator estimates, which is a known, disclosed gap, not something to paper over with a fake citation. |
| `alternatives` | Vendor **ids** (not names) of same-category substitutes. Every id must exist as `vendors/<id>.json`. |

## Local commands

```
npm run kb:check      # validate vendors/*.json + confirm src/data/vendors.generated.ts is current
npm run kb:generate   # regenerate src/data/vendors.generated.ts from vendors/*.json
```
