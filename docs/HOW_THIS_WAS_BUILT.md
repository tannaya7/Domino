# How this was built

This project was built with Claude Code (Anthropic's AI coding agent) across ~20 commits, working
from detailed, scope-bounded prompts (feature descriptions, constraints, explicit non-goals, and
time-boxes) rather than open-ended "build me an app" requests. This document says what that meant
in practice, what verification actually ran, and what a human still had to decide.

## What was AI-generated

Effectively all of it — the file-graph engine, vendor detection pipeline, availability/Monte Carlo
model, AWS integrations (Bedrock, DynamoDB, SNS, AWS Health), the PR Resilience Gate, the React UI,
the test suite, and this documentation set. There is no part of the codebase written by hand first
and then "cleaned up" by AI, or vice versa — every commit's diff was AI-authored, prompted and
reviewed by a human (`tannaya7`) turn by turn.

## What "reviewed" meant, concretely

Two different things, and this doc is careful not to conflate them:

1. **Automated verification that runs on every change** — not a one-time check, a standing gate:
   - `npm run verify:all` (wired as CI): typecheck (`tsc -b`), lint (`oxlint`), then the full test
     suite via `vitest run --reporter=json`, and `scripts/verification-report.ts` writes
     [docs/VERIFICATION.md](VERIFICATION.md) from those **actual** results — test counts, pass/fail,
     timings — never hand-typed. A red run there means a claim in that file no longer holds, not a
     stale claim someone forgot to update.
   - The availability model specifically has a differential-testing audit, not just unit tests:
     [`src/engine/correlated.test.ts`](../src/engine/correlated.test.ts) cross-validates the exact
     correlated-failure computation against a seeded Monte Carlo oracle (`runMonteCarloAvailability`)
     — two independently-implemented methods have to agree, which catches a class of bug that
     testing either method alone against hand-picked expected values would miss. See
     [docs/availability-model.md](availability-model.md) for the model itself, including two
     documented correctness bugs it fixes ("fabricated correlation risk for single-vendor
     substrates" being one — see commit `6722d43`).
   - `scripts/verify-aws.ts` exercises the AWS-integration code paths directly; its real output is
     what [docs/AWS_VERIFICATION.md](AWS_VERIFICATION.md) is grounded in, alongside a live session
     against `documenso/documenso`, `formbricks/formbricks`, and
     `stripe-samples/checkout-one-time-payments` through the real UI.
   - `server/test/scannerFuzz.test.ts` fuzzes the file scanner against pathological/generated input;
     robustness tests exercise the criticality engine on 100,000+-node synthetic graphs.
2. **Human decisions that AI verification cannot make** — scope cuts under a time-box (see git log:
   "Make the demo impossible to fail," "Make the vendor graph tell the story at a glance" — UX
   priority calls, not correctness fixes), which infrastructure tradeoff to accept when a hard
   constraint appeared (no AWS account available while building — see
   [docs/AWS_VERIFICATION.md](AWS_VERIFICATION.md) — versus a Cloudflare tunnel for a working live
   demo, an explicit choice made when this submission package was assembled, not a default), and
   what a user-facing claim is allowed to say (the recurring "unknown != healthy," "modeled
   estimate, not a guarantee" language throughout the UI and docs came from explicit direction, not
   an AI default).

## What this workflow does NOT claim

- That every line was manually re-derived by a human independent of the AI's own reasoning — it
  wasn't; the review loop above is automated-test-driven, with human judgment applied at the level
  of scope, architecture, and what's honest to claim, not line-by-line diff auditing of generated
  code.
- That AI-authored tests are inherently trustworthy evidence of correctness — this is why the
  differential/cross-validation approach above exists: a single test suite written by the same
  process that wrote the code under test can encode the same misunderstanding twice. Two
  independently-implemented methods agreeing is stronger evidence than either passing its own tests.
- That this process is faster or cheaper than traditional development — no time/cost comparison
  was tracked, and none is claimed here.

## Real numbers, not narrative

Every count in this document and in the README is generated, not typed: test counts come from
`docs/VERIFICATION.md` (itself generated by `scripts/verification-report.ts` from a real
`vitest run` on every `npm run verify:all`), and the "Why it matters" numbers in the README come
from `scripts/readme-numbers.ts` reading the actual showcase repo snapshot. If you re-run either
script and a number in this repo's docs doesn't match, the docs are stale — the scripts are the
source of truth, not this prose.
